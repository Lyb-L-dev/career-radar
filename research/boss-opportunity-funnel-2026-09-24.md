## 产品目标

把日常工作从“打开平台逐条看”改成“每天看一页可解释的候选机会，选出值得投的岗位，记录结果”。衡量有效性的是**读到值得投岗位的时间**、实际投递与面试反馈，不是抓到的岗位总数。

当前项目已经能从企业官网/官方公告抽取 JD、去重、打分、收藏和标记投递；缺口是来源发现过于依赖预设公司名单。[README](../README.md) 将第三方平台设为待核验线索，且 [岗位 API 适配](../src/career_radar/web_repository/jobs.py) 固定写了“公开页面抓取 + LLM 结构化提取”“urlVerified=True”。因此 BOSS 数据先进入**独立机会池**；它可以被阅读、收藏、跳转平台投递，不冒充官网已核验岗位，不自动进入官方日报与自动申请材料工作流。

## 第一阶段可交付的完整使用流程

1. 用户在已登录的 BOSS 浏览器中按一组岗位意图做小批量搜索：FDE/Forward Deployed Engineer、AI 应用开发、大模型应用开发、Agent 工程师；“AI 解决方案工程师”需进一步判断是否真有研发工作。城市不限，搜索时包含校招、应届、实习转正和可接受的初级社招。抓取层优先试用 [eatmoreduck/BOSS 专用 CDP 项目](boss-zhipin-sources-2026-09-24.md)；它已有列表字段映射、详情 JD 完整性检查和 JSON/CSV 导出。该工具的 CLI 每次带一个城市参数，故“城市不限”应先覆盖岗位较多的若干城市、轮换扩展并合并去重，不穷举全国，也不能误以为默认上海代表全国。登录态只留在浏览器配置中，Career Radar 只读职位数据文件，不读取 Cookie。
2. Career Radar 导入原始列表/详情，保留平台 `boss`、加密职位 ID、原始链接、导入批次、首次/最近见到时间、列表/详情各自字段及完整 JD 标记。稳定键使用平台 + 原始职位 ID；缺少稳定 ID 时只做待人工确认的弱匹配。重复导入更新快照，不重复生成“新机会”。
3. 先做明确的**硬条件**判断，再对留下的机会排序；来源缺字段时显示“需确认”，而非把未知当不合格。每条机会显示通过/排除原因及数据来源。
4. “今日值得看”按优先投递、需确认、低优先级、已排除分组。单条卡片提供原始 BOSS 链接、完整 JD、收藏、稍后看、不感兴趣、已投递和跟进结果。跳转平台由用户自己投递。
5. 后续每日导入新批次并对比变化，只提醒新出现或明显变化、且仍符合目标的机会。已投递或不感兴趣的岗位不反复提醒；无法确认岗位是否仍在线时显示“最近见到”，不推断已下架。

## 筛选规则：先资格，再投入回报

### 第一层：仅在 JD 明确时排除

- 岗位方向与用户配置的目标岗位无关，或命中用户明确排除的方向。
- 城市在本次偏好里**不作为排除或扣分条件**；仍展示工作地点、远程/驻场及出差要求，供用户判断实际生活成本。日后用户改变偏好再开启城市条件。
- 明确要求硕士/博士、指定学校层次或其他用户不满足的**硬性资格**。写“本科及以上”或未写学校背景时不能因“二本”自动排除。
- 明确要求与用户不符的毕业届别，或明显高于用户实际经历的必备工作年限。毕业年份、校招/社招/实习和初级经验岗位应作为独立字段；用户说的是“校招/应届优先”，不能把所有初级社招排除。“不限经验”保留。
- 不能证明职位归属、正文缺失、登录墙、验证码页、明显广告/培训推广时进入“需确认”，不把错误页面当正常岗位。

### 第二层：对可投机会排序

建议首版采用可解释的 100 分**阅读优先级**，不称为录取概率，权重在 UI 中可调整：

| 因素 | 初始权重 | 判断依据 |
| --- | ---: | --- |
| AI/FDE 岗位相关 | 30 | 结合标题与职责区分实际写代码/做客户问题落地，与纯销售、纯实施或研究型岗位的差异；不能只按“AI”一个关键词 |
| 应届与经验距离 | 25 | 校招、应届、实习转正优先；可投的初级社招也保留；没有标注不直接扣到底 |
| 技能与项目证据 | 25 | 例如 Python、API/后端、LLM 应用、Agent、检索/部署，以及沟通与问题交付的真实项目证据；按 JD 必需项核对，不预设用户都会 |
| JD 可用性与投递路径 | 10 | 详情完整、公司/岗位可识别、平台链接可打开 |
| 新近程度 | 10 | 有可信发布时间用发布时间；无则只用“首次/最近见到” |

显示“为什么排在前面/为什么需确认”，支持把用户自己的硬条件作为例外覆盖。公司规模、大厂身份、是否 985/211 的**推测门槛**不直接转化为一票否决；只按职位明确要求判断。外包、猎头或培训相关标签可以设为用户可配置的降权/排除项，先看证据再处理。FDE 有时写作“AI 解决方案”“客户现场工程师”等；只在 JD 中确有编码、系统集成和交付职责时算高相关，不能把同名销售岗混进来。

先用规则筛掉明显不合适的岗位，再让现有 LLM 只评估前若干条完整 JD 的技能差距与投递难度，节省时间和调用成本。LLM 负责解释与补充，不得编造学历要求、发布时间或候选人经历。

判断示例（具体职位仅为合成样例）：

| BOSS 页面可见内容 | 放入哪组 | 原因 |
| --- | --- | --- |
| “AI 应用工程师，本科，应届，Python 与 LLM 项目” | 优先投递 | 方向、学历与应届条件明确匹配；再用完整 JD 确认能力差距 |
| “FDE，经验不限，需客户现场部署，学校未限制” | 优先阅读/需确认 | 不因普通本科或非校招字样排除；核对实际编码职责与出差强度 |
| “大模型算法研究员，仅硕士，985/211” | 已排除 | JD 给出明确硬门槛；可保留记录避免下次重复阅读 |
| “AI 解决方案工程师”但 JD 只有销售指标 | 低优先级 | 标题命中 AI，职责与用户想找的工程方向不符 |
| 搜索卡片只有标题、详情页被登录墙截断 | 需确认 | 原文不足以判断学历、职责和投递资格，不能伪装成完整 JD |

**不把 BOSS 岗位直接变成 `JobPosting` 官方事实。** 当用户通过企业官网核实同一岗位时，可建立关联并保留 BOSS 原始记录、官网链接、核验时间及两者差异；申请时优先显示当前有效的实际投递入口。

## 验收与分阶段推进

- 第一里程碑：离线导入 BOSS 项目的固定 JSON 样本；重复导入幂等，坏文件不写入，职位 ID 不串岗，空白/截断 JD 标为需确认。无需真实登录即可测。
- 第二里程碑：机会池可筛选与手动投递跟踪；用用户人工标注的少量岗位检查排除理由和前 20 条值得读的比例。不要用抓取总数验收。
- 第三里程碑：在用户自己的已登录浏览器做小批量真实抓取验证，记录列表/详情成功率、验证码和限流、耗时、JD 完整性；只有这些数据达标后再考虑定时运行。
- 后续平台：只增加来源适配器和字段映射；排序、人工状态和复核逻辑复用第一阶段。不要同时为多个平台各造一套“岗位中心”。

这份方案尚未实施爬虫或修改产品代码。第一个可独立落地的工程切片是“BOSS JSON 导入 → 独立机会池 → 可解释筛选 → 手动投递跟踪”。
